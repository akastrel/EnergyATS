# Настройка и эксплуатация АВР

Этот документ — практическая памятка по настройке АВР (EnergyATS) и его связей с Home Assistant. Он описывает не внутреннюю архитектуру, а то, что важно знать при эксплуатации: что меняет каждая настройка, какие HA-сущности обязательны, какие являются вспомогательными, и какие сообщения может получить пользователь.

Нормативное поведение системы по-прежнему задаётся `REQUIREMENTS_RU.md`, а точный технический HA contract — `ENTITIES_RU.md`. Здесь информация намеренно изложена пользовательским языком.

## 1. Настройки приложения АВР

### 1.1. Общие настройки

| Параметр | Значение по умолчанию | Для чего нужен и на что влияет |
| --- | ---: | --- |
| `armed` | `false` | Главный предохранитель приложения. При `false` АВР наблюдает за системой и ведёт журнал, но не подаёт команды на контакторы, генераторы и другие исполнительные устройства. Для обычной автоматической работы должен быть `true`; первый запуск и проверку конфигурации безопаснее выполнять при `false`. |
| `tick_seconds` | `1.0` с | Период основного цикла принятия решений. Меньшее значение делает реакцию на изменения немного быстрее, но увеличивает частоту обработки. В обычной эксплуатации менять без причины не требуется. Большинство защитных выдержек времени задаются отдельными настройками и не зависят напрямую от этого параметра. |
| `log_level` | `info` | Детальность App log. `info` — нормальный эксплуатационный режим; `debug` нужен в основном для диагностики. На алгоритм управления не влияет. |

### 1.2. Реакция на исчезновение и восстановление сети

| Параметр | Значение по умолчанию | Для чего нужен и на что влияет |
| --- | ---: | --- |
| `grid_failure_delay` | `60` с | Сколько входная сеть должна непрерывно считаться отсутствующей перед тем, как АВР признает отключение реальным. Защищает от запуска генератора при коротких провалах сети. После этой выдержки либо начинается обычный запуск генератора, либо, если включён UPS Run, начинается ожидание на UPS. |
| `grid_restore_stable_time` | `60` с | Сколько восстановившаяся сеть должна непрерывно оставаться исправной перед возвратом дома на неё. Защищает от переключения на нестабильную сеть и повторных переключений при «мигающем» вводе. |
| `transfer_confirmation_timeout` | `60` с | Максимальное время ожидания физического подтверждения шага силового переключения. Если команда контакторам была подана, но ожидаемое положение не подтвердилось за это время, дальнейшее автоматическое управление этим переходом считается небезопасным и может потребовать Recovery. Увеличивать timeout следует только если реальное оборудование объективно переключается дольше. |

### 1.3. Разрешение генераторов

| Параметр | Значение по умолчанию | Для чего нужен и на что влияет |
| --- | ---: | --- |
| `generator_a_enabled` | `true` | Разрешает АВР использовать физический слот A для новых управляемых запусков. Если выключить, АВР не будет выбирать этот генератор для нового запуска. Это не команда остановить уже работающий внешний генератор. |
| `generator_b_enabled` | `true` | То же для физического слота B. |

Выбор PRIMARY, пользовательские имена генераторов и их модели находятся не в настройках приложения АВР, а в Home Assistant / Generator Controller. `select.primary_generator` определяет, какой из разрешённых генераторов АВР пытается использовать первым.

### 1.4. Load Manager — управление некритичными нагрузками

Load Manager не является обязательной частью основного АВР. При его отключении запуск генераторов, силовое переключение и возврат на сеть продолжают работать обычным образом.

| Параметр | Значение по умолчанию | Для чего нужен и на что влияет |
| --- | ---: | --- |
| `load_management_enabled` | `false` | Включает автоматическое управление группами некритичных нагрузок G1/G2 при работе от генератора. При `false` АВР не трогает эти группы. |
| `load_measurement_stabilization_time` | `10` с | Сколько ждать после включения или отключения группы нагрузки перед оценкой новой мощности генератора. Нужен, чтобы не принимать решение по переходному процессу. |
| `load_restore_margin_percent` | `15` % | Какой запас до номинальной мощности генератора должен оставаться перед автоматическим включением следующей отключённой группы. Чем больше значение, тем осторожнее восстановление нагрузки. |
| `nominal_overload_time` | `20` с | Сколько нагрузка должна непрерывно превышать номинальную мощность генератора, прежде чем Load Manager начнёт разгрузку. Короткие пики ниже этой выдержки игнорируются. |
| `maximum_overload_confirmation_time` | `4` с | Выдержка для превышения максимальной паспортной мощности. Она существенно короче номинальной, поэтому при серьёзной перегрузке нагрузка снимается быстрее. |
| `load_restore_retry_interval` | `300` с | Минимальный интервал до новой попытки вернуть нагрузку, которую ранее пришлось оставить выключенной из-за недостаточного запаса мощности или неуспешного восстановления. |

Load Manager отключает нагрузки в порядке **G2 → G1**, а возвращает их в порядке **G1 → G2**. Он автоматически включает обратно только те группы, которые ранее отключил сам АВР; пользовательский `OFF` не должен присваиваться АВР как собственное отключение.

### 1.5. UPS Run — отложенный запуск и циклическая подзарядка

UPS Run нужен для длительных отключений, когда критическая линия может некоторое время работать от батарей и нет смысла держать генератор запущенным непрерывно.

`Delayed Start` и `Charge Cycling` включаются независимо друг от друга.

| Параметр | Значение по умолчанию | Для чего нужен и на что влияет |
| --- | ---: | --- |
| `delayed_generator_start_enabled` | `false` | После подтверждённого отключения сети разрешает не запускать генератор сразу, а продолжить работу от UPS. Запуск произойдёт при выполнении первого из условий: достигнут Start SoC, достигнут минимальный TTG или истекло максимальное время ожидания. |
| `generator_charge_cycle_enabled` | `false` | Разрешает при длительном outage останавливать автоматически запущенный генератор после достижения целевого SoC, затем снова работать от UPS и при необходимости запускать генератор повторно. На ручную managed-сессию эта автоматическая остановка не распространяется. |
| `generator_start_soc` | `40` % | Нижний порог заряда UPS для запуска генератора. Чем выше порог, тем раньше запускается генератор и тем меньше глубина разряда батарей. Должен быть ниже `generator_target_charge_soc`. |
| `generator_target_charge_soc` | `80` % | Целевой заряд, после которого в автоматическом charge cycle дом снимается с генератора, генератор штатно охлаждается и останавливается. Должен быть выше Start SoC. |
| `generator_min_ttg_before_start` | `60` мин | Дополнительный критерий запуска по расчётному оставшемуся времени работы UPS. Используется только когда батарея действительно разряжается. |
| `generator_max_start_delay_hours` | `6` ч | Абсолютный предел ожидания на UPS. По его истечении генератор запускается независимо от того, что показывают SoC и TTG. Значение `0` означает отсутствие дополнительного ожидания после основной проверки пропадания сети. Отсчёт переживает restart АВР. |

Если данные UPS становятся недостоверными во время ожидания запуска, АВР не продолжает полагаться на них: Delayed Start отменяется и система переходит к обычному безопасному запуску генератора. Если генератор уже работает и идёт заряд, недостоверный SoC, наоборот, запрещает автоматическую остановку по Target SoC.

### 1.6. Scheduled Exercise — плановые пробные пуски

Для каждого физического слота A/B есть одинаковый набор настроек.

| Параметр | Значение по умолчанию | Для чего нужен и на что влияет |
| --- | ---: | --- |
| `family_presence_entity` | `group.family` | HA entity, по которому Scheduler понимает, находится ли семья дома. Используется только Scheduled Exercise и не влияет на обычную работу АВР при пропадании сети. |
| `generator_a_exercise_enabled` | `false` | Разрешает автоматические плановые пробные пуски генератора A. |
| `generator_a_exercise_interval_days` | `30` дней | Максимальный интервал без квалифицирующего запуска A, после которого пробный пуск становится due. |
| `generator_a_exercise_start_time` | `15:00` | Локальное время Home Assistant, в которое Scheduler пытается выполнить пробный запуск A. |
| `generator_a_exercise_run_minutes` | `10` мин | Минимальное время непрерывной подтверждённой работы генератора A для успешного Exercise. |
| `generator_a_exercise_presence_grace_days` | `7` дней | Сколько дней после due присутствие семьи может откладывать обычный пробный запуск A. После истечения grace действует логика принудительного запуска с предварительным уведомлением. |
| `generator_b_exercise_enabled` | `false` | Разрешает автоматические плановые пробные пуски генератора B. |
| `generator_b_exercise_interval_days` | `45` дней | Максимальный интервал без квалифицирующего запуска B. |
| `generator_b_exercise_start_time` | `15:00` | Локальное время попытки пробного запуска B. |
| `generator_b_exercise_run_minutes` | `10` мин | Минимальная длительность успешного Exercise B. |
| `generator_b_exercise_presence_grace_days` | `14` дней | Допустимая отсрочка Exercise B из-за присутствия семьи. |

Обычный Exercise требует достоверного подтверждения, что семья отсутствует, непосредственно перед физическим запуском. Для принудительного запуска после grace обязательно успешное предварительное уведомление пользователя не менее чем за 60 минут.

## 2. Сенсоры и реле в Home Assistant

### 2.1. Как понимать критичность

В этом разделе используются четыре уровня:

- **CORE / safety-critical** — без этого сигнала или исполнительного устройства АВР не может безопасно выполнять основную силовую функцию. Неопределённое состояние блокирует соответствующие действия; отказ во время операции может привести к `RECOVERY_REQUIRED`.
- **CORE / required** — сущность обязательна для штатного запуска/идентификации конфигурации, но сама по себе не является физической защитой.
- **SOFT** — отказ ограничивает только дополнительную функцию (UPS Run, Load Manager, Exercise) либо включает консервативный fallback; основной АВР должен продолжать работать.
- **OUTPUT / diagnostic** — АВР только публикует информацию; сущность не используется для принятия силового решения.

### 2.2. Основное разрешение автоматического резерва

| Entity | Критичность | Назначение |
| --- | --- | --- |
| `input_boolean.automatic_generator_transfer` | CORE / required | Разрешает автоматическую outage-сессию после подтверждённого исчезновения сети. Если выключен, автоматический запуск по Grid outage не выполняется. Ручной запрос резервного питания от этого helper не зависит. |
| `input_boolean.generator_test_mode` | SOFT | Маркер нового внешнего RUNNING как тестового запуска. Сам ничего не запускает и не останавливает. Если entity вообще отсутствует, считается `OFF`. |

### 2.3. Входная сеть и основные контакторы

| Entity | Критичность | Назначение |
| --- | --- | --- |
| `binary_sensor.grid_input_ready` | CORE / safety-critical | Главный факт пригодности внешней сети. По нему запускаются таймеры исчезновения/восстановления Grid. |
| `binary_sensor.house_powered_by_grid` | CORE / safety-critical | Feedback положения/управляющей цепи сетевого контактора. Используется для подтверждения безопасного break-before-make. |
| `binary_sensor.house_powered_by_generator` | CORE / safety-critical | Feedback генераторного контактора. Используется для подтверждения фактического подключения/отключения генераторной ветви. |
| `switch.grid_power` | CORE / safety-critical actuator | Разрешение сетевой ветви. АВР использует его при отключении Grid перед переходом на генератор и при безопасном возврате. |
| `switch.use_generator_as_power_source` | CORE / safety-critical actuator | Selector основной пары контакторов: `ON` — генераторная ветвь, `OFF` — сетевое направление. Команды всегда должны подтверждаться feedback-сигналами. |

Успешный HA service call не является подтверждением физического переключения. Решение принимается только после появления ожидаемых feedback-сигналов.

### 2.4. Генераторы A и B

| Entity | Критичность | Назначение |
| --- | --- | --- |
| `binary_sensor.generator_a_is_running` | CORE / safety-critical | Физическое подтверждение RUNNING генератора A. |
| `binary_sensor.generator_b_is_running` | CORE / safety-critical | Физическое подтверждение RUNNING генератора B. |
| `switch.generator_a_remote_start` | CORE / safety-critical actuator | Уровневый REMOTE START генератора A. `ON` не означает, что двигатель уже запустился; это проверяется `*_is_running`. |
| `switch.generator_b_remote_start` | CORE / safety-critical actuator | То же для генератора B. |
| `button.generator_a_choke_to_cold_start` | CORE actuator при ARMED | Перевод заслонки A в положение холодного запуска. Сущность должна существовать в управляемой конфигурации. |
| `button.generator_a_choke_to_run` | CORE actuator при ARMED | Перевод заслонки A в рабочее положение. |
| `button.generator_b_choke_to_cold_start` | CORE actuator при ARMED | Перевод заслонки B в положение холодного запуска. |
| `button.generator_b_choke_to_run` | CORE actuator при ARMED | Перевод заслонки B в рабочее положение. |

Одновременный `RUNNING=ON` у A и B сам по себе допустим. Какой генератор фактически владеет общей генераторной шиной, АВР определяет отдельно.

### 2.5. Safety

| Entity | Критичность | Назначение |
| --- | --- | --- |
| `switch.generators_emergency_stop` | CORE / safety-critical | Аппаратно-логический запрет работы генераторов. `ON` немедленно имеет приоритет над обычной автоматикой. Неизвестное состояние не считается безопасным разрешением на новый запуск. |
| `sensor.garage_temperature` | SOFT | Используется для выбора заслонки и времени прогрева. При отсутствии температуры Generator Controller применяет консервативный режим; core ATS не должен останавливаться только из-за этого сенсора. |

### 2.6. Имена, модели и PRIMARY

| Entity | Критичность | Назначение |
| --- | --- | --- |
| `sensor.generator_a_name` | CORE / required | Пользовательское имя физического слота A. Используется в статусах, сообщениях и сопоставлении PRIMARY. |
| `sensor.generator_b_name` | CORE / required | Пользовательское имя физического слота B. |
| `sensor.generator_a_model` | CORE / required | Модель генератора A для метаданных/статуса. |
| `sensor.generator_b_model` | CORE / required | Модель генератора B. |
| `select.primary_generator` | CORE / required | Выбирает генератор, который АВР пытается использовать первым. Значение должно совпадать с одним из опубликованных имён генераторов. |

### 2.7. Паспортная мощность генераторов — Load Manager

| Entity | Критичность | Назначение |
| --- | --- | --- |
| `sensor.generator_a_nominal_power` | SOFT | Номинальная допустимая активная мощность A, W. Нужна только Load Manager. |
| `sensor.generator_a_maximum_power` | SOFT | Максимальная мощность A, W. |
| `sensor.generator_b_nominal_power` | SOFT | Номинальная мощность B, W. |
| `sensor.generator_b_maximum_power` | SOFT | Максимальная мощность B, W. |

Если эти данные некорректны или недоступны, Load Manager должен перейти в локальный `DEGRADED`, но основной АВР не должен переходить из-за этого в системный Recovery.

### 2.8. UPS Run

| Entity | Критичность | Назначение |
| --- | --- | --- |
| `sensor.ups_battery_charge_level_soc` | SOFT | SoC батарей UPS, %. Используется для Start SoC и Target Charge SoC. |
| `sensor.ups_battery_time_remaining_minutes_ttg` | SOFT | Расчётное оставшееся время работы UPS, минуты. |
| `binary_sensor.ups_running_on_battery` | SOFT | Показывает реальный разряд батарей. TTG как критерий запуска используется только при `ON`. |
| `binary_sensor.ups_ready` | SOFT | Общая готовность UPS/АКБ; должен отражать отсутствие критического состояния батареи и способность продолжать работу. |

При выключенном UPS Run эти сущности не влияют на core ATS.

### 2.9. Load Manager

Управляемые группы:

| Entity | Критичность | Назначение |
| --- | --- | --- |
| `switch.non_critical_loads_first_floor` | SOFT actuator | G1 — некритичные нагрузки 1-го этажа. Восстанавливаются первыми, отключаются после G2. |
| `switch.non_critical_loads_basement_floor` | SOFT actuator | G2 — некритичные нагрузки цокольного этажа. При перегрузке отключаются первыми. |

Измерение генераторной шины:

| Entity | Критичность | Назначение |

| `sensor.generator_power` | SOFT, основной для Load Manager | Активная мощность, W. Именно по этому сигналу принимаются решения о допуске/сбросе нагрузки. Поток измерений должен реально обновляться. |
| `sensor.generator_current` | SOFT / diagnostic | Ток генератора. Сейчас используется для диагностики, а не для основного решения Load Manager. |
| `sensor.generator_voltage` | SOFT / diagnostic | Напряжение генератора. |
| `sensor.generator_apparent_power` | SOFT / diagnostic | Полная мощность. |
| `sensor.generator_reactive_power` | SOFT / diagnostic | Реактивная мощность. |
| `sensor.generator_power_factor` | SOFT / diagnostic | Коэффициент мощности. |
| `sensor.generator_frequency` | SOFT / diagnostic | Частота. |

Отказ meter/G1/G2 или ошибка команды группе нагрузки не должны сами по себе блокировать возврат Grid или переводить весь АВР в `RECOVERY_REQUIRED`.

### 2.10. Presence для Scheduled Exercise

| Entity | Критичность | Назначение |
| --- | --- | --- |
| entity из `family_presence_entity` (`group.family` по умолчанию) | SOFT | Используется только Scheduler-ом. Для обычного Exercise требуется достоверно определить отсутствие семьи. `unknown/unavailable` откладывает обычный пробный запуск, но не влияет на core ATS. |

### 2.11. Состояние АВР, публикуемое в HA

| Entity | Критичность | Назначение |
| --- | --- | --- |
| `sensor.energy_ats_status` | OUTPUT / diagnostic | Основной read-only статус АВР. Содержит человекочитаемое состояние и технические атрибуты `source`, `phase`, active generator, PRIMARY, remaining time, UPS Run, Load Manager и Exercise. Не используется как вход для собственной силовой логики АВР. |

Особенно полезный машинный атрибут:

```text
phase: recovery_required
```

Он означает, что АВР находится в аварийной блокировке и автоматические аппаратные действия запрещены до безопасного Recovery.

## 4. Сообщения и нотификации

Этот раздел — рабочий каталог пользовательских сообщений. Его цель — отдельно согласовать формулировки, а затем синхронно внести утверждённый текст в код/каталог сообщений.

### 4.1. Как сейчас доставляются сообщения

- Все `MAIN` и `DETAIL` события пишутся в App log.
- Только `MAIN` события публикуются в основной Home Assistant Logbook.
- Любое событие уровня `critical` в режиме `ARMED` дополнительно отправляется через `script.notify_critical`, независимо от `MAIN/DETAIL`.
- Обычный `warning` сам по себе push-уведомление не создаёт.
- Некоторые предупреждения Load Manager дополнительно явно отправляются пользователю через notification path.
- Предупреждение перед принудительным Scheduled Exercise отправляется отдельно и синхронно: Scheduler обязан получить подтверждение успешной доставки.
- В режиме `DISARMED` пользовательские push-уведомления, связанные с управляемой работой АВР, не отправляются.

### 4.2. CRITICAL — критические пользовательские нотификации

#### C1. АВР перешёл в аварийную блокировку

**PUSH.** Универсальное сообщение при переходе Supervisor в `RECOVERY_REQUIRED`:

> АВР остановил автоматическое управление: `{reason}`. Требуется безопасное восстановление.

Причиной могут быть E-STOP, неоднозначная силовая топология, ошибка силового перехода, отказ генератора без допустимого fallback, незавершённая операция после restart и другие ситуации, в которых АВР больше не имеет права продолжать управление «по догадке».

#### C2. Fallback на резервный генератор

**PUSH.**

> `{failed}` недоступен: `{reason}` Запускаем резервный `{secondary}`; это единственная автоматическая попытка переключения на второй генератор.

#### C3. Управляемый генератор отказал, но второй уже работает как внешний

**PUSH.**

> Отказ `{failed}`: `{reason}` Работающий `{other}` остаётся внешним.

#### C4. Scheduled Exercise завершился аварией

**PUSH.**

> Пробный запуск `{generator}` завершился неуспешно: `{reason}`.

#### C5. Load Manager: критическая перегрузка, отключать больше нечего

**PUSH.**

> Критическая перегрузка генератора `{generator}`: нагрузка `{power}` Вт. Все управляемые некритичные нагрузки уже отключены.

#### C6. Load Manager: диагностическое сообщение той же критической перегрузки

Сейчас это отдельное `DETAIL critical`, поэтому оно также попадает в `script.notify_critical`:

> Диагностика Load Manager: нагрузка `{power}` Вт превышает максимальный предел `{threshold}` Вт; доступных групп для отключения нет.

**Замечание для последующей правки:** сейчас C5 и C6 дают две push-нотификации об одной критической перегрузке. Вероятно, пользовательским push следует оставить C5, а C6 сохранить только как DETAIL/App log.

#### C7. Потеря Home Assistant во время незавершённой физической операции

Supervisor формирует критическое событие:

> Потеряна связь с Home Assistant во время незавершённой силовой операции. АВР перешёл в безопасное восстановление и не будет угадывать положение оборудования.

Пока Home Assistant недоступен, отправить HA push физически невозможно. После reconnect это промежуточное сообщение отдельно не отправляется; пользователь получает итоговый CRITICAL C1 с причиной перехода в Recovery. Непосредственно в App log потеря связи фиксируется сразу.

### 4.3. WARNING — Core ATS / Supervisor

Обычные `WARNING` ниже не создают push автоматически; `MAIN` попадает в HA Logbook, `DETAIL` остаётся только в App log.

1. `АВР ожидает {seconds} с, чтобы исключить кратковременный сбой сети.`
2. `Дом переведён на резервное питание от {generator}.`
3. `Генераторную шину фактически питает внешний {generator}. АВР не управляет его остановкой.`
4. `Входная сеть снова пропала во время возврата на сеть. Возврат отменён; сохраняем доступное резервное питание.`
5. `Managed-запуск отклонён: уже работает внешний генератор ({names}).`
6. `{generator} сейчас недоступен; новый запуск не начат.`
7. `Сброс отклонён: {причина}.`
8. `Восстановление не завершено: {reason}.`
9. При потере HA в устойчивом состоянии App log содержит предупреждение о недоступности Home Assistant и временной блокировке управляющих команд. Отдельным пользовательским событием после reconnect оно сейчас не воспроизводится.

### 4.4. WARNING — наблюдаемые физические изменения

1. `Входная сеть 220 В пропала.`
2. `Состояние входной сети 220 В стало неизвестно.`
3. `{generator}: состояние REMOTE START стало неизвестно.` — DETAIL.
4. `{generator}: состояние RUNNING стало неизвестно.`
5. `Фактический источник генераторной шины изменился: {old} → {new}.` — WARNING только если новый owner неизвестен; DETAIL.
6. `Активирован аварийный STOP генераторов. АВР блокирует дальнейшее автоматическое управление.`
7. `Состояние аварийного STOP генераторов стало неизвестно.`
8. `Положение основных силовых вводов стало неизвестно.` — DETAIL.
9. `Подтверждено: питание дома отсутствует.` — DETAIL.
10. `Источник питания дома стал неизвестен.` — DETAIL.

При `Emergency Stop = ON` вслед за warning обычно возникает системный `RECOVERY_REQUIRED`, и пользователь дополнительно получает CRITICAL C1.

### 4.5. WARNING — UPS Run

1. `Некорректны настройки Delayed Start / Charge Cycling.`
2. `Данные UPS недостаточно надёжны для дальнейшего ожидания. Отложенный запуск отменён; переходим к обычному безопасному запуску генератора.`
3. `Данные уровня заряда или готовности UPS недостоверны; автоматическая остановка по уровню заряда запрещена.`

Эти сообщения сейчас являются warning events и сами по себе push не создают.

### 4.6. WARNING — Scheduled Exercise

При передаче уже работающего Exercise реальному outage формируется:

> Во время пробного запуска пропала входная сеть. Уже работающий `{generator}` используется для резервного питания дома без остановки и повторного запуска.

Это `WARNING`, не push.

Отдельно существует специальное уведомление перед **forced Exercise**. Оно не является `WARNING SupervisorEvent`, а отправляется как подтверждаемая пользовательская нотификация:

> Пробный запуск генератора `{generator}` состоится `{day_word}` в `{start_time}`. Это регулярная проверка работоспособности генератора. После запуска генератор будет автоматически остановлен через `{minutes}` минут.

Его успешная доставка является safety prerequisite для последующего принудительного пробного запуска.

### 4.7. WARNING и пользовательские нотификации Load Manager

У Load Manager есть локальные неисправности, которые не должны переводить весь АВР в system Recovery, но о некоторых из них пользователь уведомляется отдельно.

#### L1. Load Manager перешёл в DEGRADED

**PUSH при первом переходе в состояние деградации:**

> Автоматическое управление некритичными нагрузками временно недоступно. Основное управление резервным питанием продолжает работу.

Техническая причина отдельно записывается как DETAIL:

> Диагностика Load Manager: `{reason}`

Причиной могут быть неизвестный фактический генератор, некорректные Nominal/Maximum limits, недоступный generator meter, отсутствие свежего измерения мощности, неизвестное состояние G1/G2, stale stream мощности и другие локальные проблемы Load Manager.

#### L2. Перед переходом на генератор не удалось отключить часть нагрузок

**PUSH:**

> Не удалось отключить часть некритичных нагрузок перед переходом на генератор. Переход на резервное питание продолжится.

Для конкретной группы возможна более точная формулировка:

> Не удалось отключить `{group}` перед переходом на генератор. Переход на резервное питание продолжится.

#### L3. Не удалось отключить группу для разгрузки генератора

**PUSH:**

> Не удалось отключить `{group}` для снижения нагрузки генератора.

#### L4. После возврата Grid не удалось восстановить группу

**PUSH:**

> После возврата основной сети не удалось автоматически восстановить `{group}`.

#### L5. Универсальная ошибка изменения группы

**PUSH fallback:**

> Не удалось автоматически изменить состояние: `{group}`.

#### L6. Номинальная перегрузка, а отключать больше нечего

**PUSH:**

> Перегрузка генератора `{generator}`: нагрузка `{power}` Вт. Все управляемые некритичные нагрузки уже отключены.

Это отличается от CRITICAL C5: здесь превышен номинальный предел, а не Maximum Power.

#### L7. Группа успешно отключена из-за перегрузки

`WARNING`, но не push:

> Из-за перегрузки генератора `{generator}` отключены `{group}`.

### 4.8. Что следует учитывать при редактировании формулировок

1. Пользовательский текст не должен содержать внутренние имена FSM, `bus owner`, `sample id`, `cycle_owned` и другие детали реализации, если без них можно объяснить ситуацию нормальным эксплуатационным языком.
2. `CRITICAL` должен означать ситуацию, о которой пользователь действительно должен узнать немедленно; диагностические подробности лучше оставлять в DETAIL/App log.
3. `WARNING` должен описывать либо значимое изменение физического состояния, либо локальную проблему, при которой основная функция АВР ещё способна продолжать работу.
4. Изменение текста в этом документе само по себе не меняет runtime. После согласования формулировок их необходимо перенести в `user_messages_ru.py` и оставшиеся прямые сообщения в коде, сохранив соответствующие уровни severity и правила доставки.

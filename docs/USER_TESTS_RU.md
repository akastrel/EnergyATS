# EnergyATS — физические испытания

## 1. Назначение

Этот документ описывает **физический commissioning EnergyATS на реальном оборудовании**. Его задача — проверить то, чего не могут доказать автоматические tests: реальные генераторы, контакторы, DKG116, feedback-цепи, МАП/АКБ, SDM120, Modbus, управляемые нагрузки и фактическое время переходных процессов.

Фактические результаты commissioning фиксируются отдельно в [`USER_TEST_RESULTS_RU.md`](USER_TEST_RESULTS_RU.md).

Здесь намеренно нет полного перебора программных комбинаций. Если сценарий отличается только перестановкой A/B или сочетанием уже проверенных software states и не добавляет нового физического риска, он должен проверяться автоматическими tests, а не повторяться на электроустановке.

## 2. Принцип отбора физических тестов

Физический тест включается сюда, только если он проверяет хотя бы один из следующих рисков:

- реальный запуск, прогрев, остановку или отказ конкретного генератора;
- фактическую коммутацию Grid / Generator либо аппаратный FIFO генераторной шины;
- реальную feedback-цепь и timing оборудования;
- качество электропитания и поведение генератора под нагрузкой;
- взаимодействие с МАП/зарядом АКБ;
- реальные G1/G2, SDM120 или Modbus;
- безопасное сохранение работающей физической системы при restart App.

Комбинационная policy-логика, ownership без нового физического эффекта, симметричные A/B permutations и искусственные fault-injection без безопасного штатного способа остаются областью automated tests/HIL.

## 3. Безопасность и фиксация результата

Используйте только штатные органы управления и заранее понятные безопасные способы имитации отказов. Не переставляйте провода, не удерживайте контакторы вручную и не обходите аппаратные блокировки ради теста.

Если питание дома ведёт себя не так, как ожидается, тест прекращается до выяснения причины.

Во время обычного функционального теста достаточно записать:

```text
TEST:
Дата/время:
PASS / FAIL:

Grid: есть / нет
Дом: Grid / Generator <имя> / UPS_ONLY / без питания
Elemax: RUNNING / STOPPED
Вепрь: RUNNING / STOPPED

Что произошло фактически:
```

Для электрических и нагрузочных тестов дополнительно записывайте доступные параметры generator bus:

```text
U, V:
I, A:
Hz:
P, W:
S, VA:
Q, var:
PF:
```

При FAIL полезно сохранить screenshot `sensor.energy_ats_status`, журнал EnergyATS и время события.

Термины:

- **PRIMARY** — генератор, который EnergyATS пытается использовать первым;
- **SECONDARY** — второй разрешённый генератор для единственного fallback;
- **restart App** — перезапуск только EnergyATS без перезапуска Home Assistant.

## 4. Core ATS commissioning

Эти проверки подтверждают базовую работу АВР и обоих физических генераторов. Выполняйте их по порядку.

### M1. Нормальная работа при исправной Grid

**Проверяет:** отсутствие самопроизвольных аппаратных действий.

**Что сделать.** Остановить оба генератора, убедиться, что Grid доступна и дом питается от неё. 1–2 минуты ничего не делать.

**Ожидается.** Дом остаётся на Grid, оба генератора остановлены, аппаратных команд без причины нет, Recovery отсутствует.

### M2. Полный ручной цикл PRIMARY

**Проверяет:** физический start/choke/warmup, transfer на generator, возврат Grid, cooldown и stop одного генератора.

**Что сделать.** Выбрать первый исправный генератор PRIMARY, дать команду перейти на резерв, дождаться устойчивого питания дома от него, затем дать команду вернуться на Grid.

**Ожидается.** Generator запускается один раз, после готовности принимает дом, при завершении сначала дом возвращается на Grid и только затем generator штатно останавливается.

### M3. Полный ручной цикл второго генератора

**Проверяет:** что второй физический generator, его DKG116, choke/REMOTE и генераторный контактор также реально работают.

**Что сделать.** Назначить второй generator PRIMARY и повторить M2.

**Ожидается.** Второй generator проходит тот же полный физический цикл. Первый остаётся остановлен.

Этот тест заменяет необходимость повторять все ATS-сценарии с переставленными A/B: общая software-логика слотов проверяется автоматическими tests, а M2/M3 подтверждают различающееся физическое оборудование.

### M4. Grid debounce в обе стороны

**Проверяет:** реальные входные сигналы Grid не вызывают лишние start/return на коротких провалах.

Время в этом тесте отсчитывается по фактическому состоянию `binary_sensor.grid_input_ready`, а не по длительности отключения внешнего ввода. Установленное реле напряжения после возвращения внешней сети проверяет её около 30 секунд; всё это время `grid_input_ready` остаётся `OFF` и этот интервал входит в `grid_failure_delay`.

**Часть A — краткая потеря Grid.** При включённом automatic transfer кратко отключить и вернуть внешнюю Grid. Убедиться, что фактический непрерывный период `grid_input_ready = OFF`, включая проверку сети реле напряжения, остаётся меньше рабочего `grid_failure_delay = 60 с`.

**Ожидается.** Generator не запускается.

**Часть B — краткое возвращение Grid.** Во время устойчивого питания дома от generator вернуть внешнюю Grid и дождаться, когда после проверки реле напряжения `grid_input_ready` фактически станет `ON`. До истечения `grid_restore_stable_time` снова убрать Grid; stable interval отсчитывается только от фактического перехода `grid_input_ready` в `ON`.

**Ожидается.** Дом остаётся на generator; возврат и остановка не начинаются из-за краткого появления Grid.

### M5. Полный automatic outage и возврат Grid

**Проверяет:** основной unattended ATS path от физической потери Grid до штатного завершения outage.

**Что сделать.** При исправном PRIMARY и включённом automatic transfer штатно отключить внешнюю Grid. Не вмешиваться до перехода дома на generator. Затем восстановить Grid и дождаться завершения цикла.

**Ожидается.** После `grid_failure_delay` PRIMARY запускается и после готовности принимает дом. После непрерывной `grid_restore_stable_time` дом возвращается на Grid, затем generator проходит cooldown и останавливается.

### M6. PRIMARY недоступен — физический fallback на SECONDARY

**Проверяет:** что после реального отказа запуска PRIMARY система способна запустить второй физический generator и передать ему дом.

**Что сделать.** Безопасным обратимым способом сделать PRIMARY недоступным для успешного запуска. SECONDARY оставить полностью исправным. Затем выполнить automatic outage как в M5.

**Ожидается.** PRIMARY получает одну managed попытку; после failure запускается SECONDARY и дом получает питание от него. A→B→A ping-pong не происходит.

Повторять этот же тест с переставленными ролями не требуется: M2/M3 уже проверяют физическую работоспособность обоих generators, а симметрию fallback policy проверяют automated tests.

### M7. Emergency Stop

**Проверяет:** физический safety-запрет не обходится manual/automatic командой.

**Что сделать.** При Grid и остановленных generators включить `switch.generators_emergency_stop`, затем запросить резервное питание.

**Ожидается.** Нового запуска и transfer на generator нет; EnergyATS показывает safety/recovery состояние. После снятия E-stop выполняется штатное восстановление.

## 5. Переходные состояния и физическая топология

Эти тесты нужны потому, что в них существенны реальные контакторы, history bus owner, feedback или restart работающей установки.

### R1. Restart EnergyATS при устойчивом питании от generator

**Проверяет:** restart App не нарушает уже установленное физическое питание и не выдаёт duplicate start/stop.

**Что сделать.** Перевести дом на managed generator и дождаться устойчивого состояния. Перезапустить только EnergyATS App, не меняя оборудование.

**Ожидается.** Generator продолжает работать, питание дома не прерывается, повторный REMOTE START/OFF не выдаётся. После восстановления App обычный возврат на Grid работает штатно.

### R2. Два RUNNING и аппаратный FIFO takeover

**Проверяет:** уникальную физическую особенность установки — оба двигателя могут RUNNING одновременно, но generator bus owner только один и меняется аппаратно.

**Что сделать.** Дать одному generator устойчиво питать дом. Второй generator штатно запустить независимо от EnergyATS и убедиться, что оба RUNNING. Затем штатно остановить текущего bus owner.

**Ожидается.** Второй RUNNING сам по себе не вызывает системную аварию и не отбирает bus. После остановки первого аппаратная схема автоматически передаёт bus второму; одновременного подключения A/B к общей bus нет.

Если включён Load Manager, в этом же тесте дополнительно проверьте, что после takeover active Nominal/Maximum относятся к новому фактическому bus owner и перед новыми power-based действиями проходит новый stabilization. Отдельный дублирующий тест ради этого не нужен.

### R3. Grid снова пропала во время возврата

**Проверяет:** реальный переход Generator → Grid не разворачивается вслепую при изменении Grid посреди физической коммутации.

**Что сделать.** Во время обычного возврата с generator на Grid убрать внешнюю Grid до полного подтверждения завершения возврата.

**Ожидается.** EnergyATS не останавливает пригодный generator только потому, что возврат уже был начат. Система доходит до безопасно подтверждаемого состояния и снова использует существующий generator без бессмысленного stop/new cold start.

### R4. Manual stop при продолжающемся outage и ownership Grid path

**Проверяет:** `REQ-BEH-14` и regression F1 — EnergyATS восстанавливает только тот Grid path, обязанность за который создал сам.

**Что сделать.** При отсутствующей Grid дождаться устойчивого питания дома от managed generator и дать команду завершить резерв, не возвращая Grid. Дождаться `UPS_ONLY` и полной остановки generator. Затем вернуть Grid и не включать `grid_power` вручную.

**Ожидается.** Generator source сначала снимается, двигатель штатно останавливается, автоматического повторного запуска до Grid/new manual request нет. После непрерывной `grid_restore_stable_time` EnergyATS сам восстанавливает принадлежащий ему Grid path.

**Restart-вариант.** После остановки generator, но до восстановления Grid, один раз перезапустить только EnergyATS. После возвращения Grid обязанность восстановления должна сохраниться.

**Отрицательный контроль ownership.** В отдельном устойчивом состоянии с физически исправной Grid намеренно выключить `grid_power` вне managed stop-сценария. EnergyATS не должен считать это outage и не должен сам отменять чужое намеренное отключение.

### R5. Потеря PRIMARY под нагрузкой и медленный fallback SECONDARY

**Проверяет:** `TC-CORE-25` на реальной feedback-схеме — исчезновение generator voltage не подменяет подтверждение положения selector, а SECONDARY получает свой полный допустимый start interval.

**Что сделать.** Только если есть безопасный штатный способ. Во время managed outage дать PRIMARY устойчиво питать дом, затем безопасно вызвать его отказ так, чтобы fallback был разрешён. Наблюдать последовательность `RUNNING` PRIMARY, `use_generator_as_power_source`, `house_powered_by_generator` и `RUNNING` SECONDARY.

**Ожидается.** При потерянном source и подтверждённо выбранной generator branch EnergyATS выполняет безопасный break/de-select и ждёт подтверждения. SECONDARY не получает преждевременный Recovery только из-за того, что его реальный start дольше старого transfer-feedback interval, но остаётся в пределах собственного start timeout. После готовности SECONDARY generator branch выбирается снова и дом получает питание.

Этот тест обязателен, чтобы считать fallback полностью подтверждённым именно на данной feedback-схеме; если безопасно вызвать такой отказ невозможно, software coverage остаётся, а физический сценарий помечается как не выполненный.

## 6. Электрический acceptance генераторов

Эти проверки относятся прежде всего к самой электроустановке. Они важнее многих combinatorial ATS-сценариев, потому что pytest не может доказать качество напряжения или устойчивость generator + MAP.

### P1. Реальная нагрузка каждого generator, включая MAP/заряд АКБ

**Проверяет:** качество питания и устойчивость каждого generator при реальной house load и наиболее тяжёлом известном режиме — работе с МАП/зарядом батарей.

**Что сделать.** Отдельно для каждого generator дать дому устойчиво питаться от него. Зафиксировать параметры при небольшой нагрузке и при обычной рабочей нагрузке. Затем, только в безопасном режиме, проверить переход к работе с МАП и фактическим зарядом АКБ.

**Записывать:** `U`, `I`, `Hz`, `P`, `S`, `Q`, `PF`, а также фактический режим МАП и момент начала/изменения заряда.

**Ожидается.** Нет опасного роста/провала напряжения, нестабильной частоты, дребезга контакторов, самопроизвольной защиты generator или DKG116 voltage fault. EnergyATS не выполняет необоснованных transfer/start/stop из-за самого изменения нагрузки.

Не создавайте намеренно перегрузку выше безопасного режима ради этого теста.

### P2. Продолжительная работа

**Проверяет:** тепловую/временную устойчивость реального двигателя, контакторов, feedback, счётчика и связи, которую короткий functional test не показывает.

**Что сделать.** После успешного P1 оставить каждый generator, который планируется использовать unattended, работать 1–2 часа под обычной реальной нагрузкой.

**Ожидается.** Нет самопроизвольных transfer, повторных REMOTE, неожиданных остановок, накопления communication faults, опасного ухода U/Hz или повторяющихся DKG/ATS ошибок.

## 7. Load Manager commissioning

Этот раздел выполняется только если `load_management_enabled=true`.

### L1. Pre-transfer shedding и последовательный admission

**Проверяет:** реальные G1/G2, их wiring и фактическую работу meter-driven admission.

**Что сделать.** Перед переходом на generator включить обе управляемые группы. Выполнить обычный managed transfer.

**Ожидается.** После готовности generator, непосредственно перед transfer, EnergyATS снимает доступные G1/G2. После подтверждённого generator supply измеряет base load и возвращает нагрузки по одной: `G1 -> G2`, только если хватает мощности и пройден новый stabilization.

### L2. User-OFF не становится ownership EnergyATS

**Проверяет:** EnergyATS не включает нагрузку, которую пользователь сам оставил OFF.

**Что сделать.** Перед generator transfer вручную оставить одну группу OFF, вторую ON. Выполнить переход на generator и затем возврат на Grid.

**Ожидается.** Изначально user-OFF группа остаётся OFF на всех этапах. Автоматически восстанавливаются только группы с доказанным `shed_by_energy_ats`.

### L3. Sustained overload → shedding → возврат Grid

**Проверяет:** реальную цепочку meter → overload timer → G2/G1 и последующее восстановление собственных OFF.

**Что сделать.** При устойчивом generator supply постепенно добавить безопасную обычную нагрузку так, чтобы `P` стало выше Nominal Power и держалось дольше `nominal_overload_time`, не создавая опасный режим. После подтверждённого shedding восстановить Grid.

**Ожидается.** Краткий spike не переключает группы. При непрерывном превышении сначала снимается G2, затем при необходимости G1, с новым measurement после каждого действия. Generator не останавливается только из-за Load Manager overload. После confirmed Grid path EnergyATS восстанавливает только собственные shed groups.

### L4. Потеря и восстановление generator meter — optional

**Проверяет:** реальный Modbus/SDM120 failure остаётся локальной деградацией Load Manager.

**Что сделать.** Выполнять только если meter можно безопасно сделать недоступным без вмешательства в силовую схему. Во время устойчивого generator supply прекратить получение новых данных, затем восстановить их.

**Ожидается.** Core ATS и питание дома продолжаются. G1/G2 не начинают самопроизвольно переключаться на stale data; системный Recovery только из-за meter не возникает. После возврата данных новый power-based action возможен лишь после свежего stabilization window.

## 8. UPS Run commissioning

Глубоко разряжать АКБ ради теста не требуется. Для наблюдения переходов допустимо временно приблизить Start/Target thresholds к текущему безопасному SoC, затем вернуть рабочие значения.

### U1. UPS-only wait и manual request

**Проверяет:** реальный режим `UPS_ONLY`, battery telemetry и немедленное прекращение автоматического ожидания по явной команде пользователя.

**Что сделать.** Включить Delayed Start при достаточном SoC/TTG и штатно отключить Grid. После `grid_failure_delay` убедиться, что generator не запущен и критическая линия работает от UPS. Затем запросить резервное питание.

**Ожидается.** До manual request дом остаётся в `UPS_ONLY` без generator start. После команды начинается обычная manual managed session без дополнительного ожидания по SoC/TTG.

### U2. Один полный automatic charge cycle

**Проверяет:** физическую последовательность Generator → UPS_ONLY при Target SoC и начало следующего UPS wait.

**Что сделать.** Включить cycling, задать безопасные временные Start/Target thresholds и дождаться automatic start. После достижения Target наблюдать полный переход.

**Ожидается.** Дом снимается с generator branch, подтверждается `UPS_ONLY`, затем generator проходит cooldown и stop. Новый generator не запускается немедленно; начинается следующий UPS wait. Если между циклами вернуть Grid, после stable time дом возвращается на Grid без нового generator start.

Manual override Target SoC отдельно физически не повторяется: это policy-arbitration без нового аппаратного эффекта и должно быть покрыто automated tests.

## 9. Scheduled Exercise commissioning

Этот раздел выполняется, если Scheduled Exercise включается для unattended использования.

### X1. Обычный полный Scheduled Exercise

**Проверяет:** сам базовый maintenance lifecycle на реальном generator — до проверки handoff-сценариев.

**Что сделать.** Для одного generator безопасно подготовить due/window так, чтобы ordinary Exercise был разрешён, а presence достоверно показывал отсутствие семьи. Grid должна быть устойчивой.

**Ожидается.** Scheduler запускает нужный generator через обычный GC; дом всё время остаётся на Grid и generator branch дома не выбирается. После требуемой RUNNING duration выполняются cooldown/stop и результат `SUCCESS`.

После X1 тот же базовый lifecycle отдельно для второго generator обычно не требуется, если M2/M3 уже подтвердили его физический start/stop, а automated tests подтверждают независимый schedule обоих slots.

### X2. RUNNING Exercise → Manual reserve

**Проверяет:** физический handoff уже работающего generator без бессмысленного OFF/new start.

**Что сделать.** Во время подтверждённого RUNNING ordinary Exercise при остающемся питании дома от Grid запросить резервное питание.

**Ожидается.** Тот же generator продолжает RUNNING, принимает manual managed session и после обычных prerequisites питает дом. Duplicate REMOTE/start нет; Exercise фиксируется как нейтрально прерванный manual handoff, а не technical failure.

### X3. RUNNING Exercise → real Grid outage

**Проверяет:** физический Exercise→Outage handoff.

**Что сделать.** Во время подтверждённого RUNNING Exercise штатно убрать Grid и дождаться `grid_failure_delay`.

**Ожидается.** Исправный уже работающий generator не останавливается ради нового cold start. После явного handoff тот же generator принимается managed outage-session и может питать дом; исходный exercise timer больше не останавливает его под outage load. После возврата Grid outage завершается штатно.

## 10. Что намеренно не проверяется отдельным тестом на реальном доме

Следующие сценарии не удалены из требований/automated tests, но **не являются отдельными commissioning tests**, потому что не добавляют самостоятельного физического риска или требуют искусственной небезопасной fault injection:

- повтор M5 с другим PRIMARY — физическую разницу generators уже проверяют M2/M3;
- fallback в обратном направлении — симметрию slots проверяет software, физический fallback проверяет M6;
- отказ и PRIMARY, и SECONDARY ради проверки отсутствия ping-pong — это Supervisor policy;
- внешний TEST_RUN только ради классификации run-context — это software ownership/classification;
- искусственное отсутствие contactor feedback без штатного безопасного способа — это automated/HIL fault-injection;
- повтор core ATS с выключенным Load Manager — disabled path покрывается automated tests, а core уже проверен M1–M7;
- manual override Target SoC — отдельная policy-комбинация без нового силового механизма;
- отдельный Load Manager test только ради A↔B limits — этот физический факт проверяется как дополнительное наблюдение в R2.

Если конкретная неисправность реально проявилась на установке, для неё можно временно добавить диагностический физический сценарий. После диагностики он остаётся в постоянном наборе только если доказано, что проверяет уникальный физический риск.

## 11. Когда считать commissioning завершённым

Для базового ATS перед unattended эксплуатацией должны быть пройдены **M1–M7**, **R1–R4** и **P1**. R5 нужен, чтобы считать реальный fallback/feedback полностью подтверждённым на установленной схеме; выполняйте его только при наличии безопасного способа вызвать отказ PRIMARY. P2 рекомендуется завершить до длительной unattended эксплуатации каждого generator.

Если включён Load Manager, дополнительно требуются **L1–L3**; L4 выполняется при наличии безопасного способа отключить meter data. Если используется UPS Run, дополнительно требуются **U1–U2**. Если включён Scheduled Exercise, сначала обязателен **X1**, затем для полноценной проверки взаимодействия с основной ATS-логикой выполняются **X2–X3**.

После первой реальной серии тестов фиксируйте только отклонения, которые действительно требуют изменения требований, software-модели либо этого commissioning-плана. Не добавляйте симметричный или комбинационный тест только ради увеличения количества сценариев.

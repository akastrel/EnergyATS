# Требования к реализации EnergyATS

## 1. Назначение документа

Этот документ определяет требуемое поведение EnergyATS для фактически существующей электрической схемы дома.

Физическая схема, аппаратные блокировки, контакторы, датчики и автоматические аппаратные переходы описываются отдельно в `PHYSICAL_POWER_TOPOLOGY_RU.md`. Этот документ является источником истины о том, как физически работает электроустановка.

`REQUIREMENTS_RU.md` отвечает на другой вопрос: **как EnergyATS должен вести себя, наблюдая и управляя этой физической схемой**.

Код не является источником требований.

---

## 2. Основные принципы

### REQ-PRINCIPLE-01. Запрещено всё, что явно не разрешено

EnergyATS не должен выполнять аппаратные действия или автоматически переходить в сценарии, которые явно не описаны требованиями.

Если безопасное действие не следует однозначно из требований, автоматика прекращает активное управление, сохраняет наблюдаемость и сообщает пользователю причину.

### REQ-PRINCIPLE-02. Физическая схема первична

Если программная модель противоречит физическому поведению оборудования, исправляется программная модель.

### REQ-PRINCIPLE-03. Команда и подтверждение — разные факты

Состояние управляющего реле означает требуемое состояние управляющей схемы. Успешный HA service call сам по себе не является подтверждением физического переключения.

### REQ-PRINCIPLE-04. Не угадывать неоднозначную физическую ситуацию

Если по доступным данным невозможно однозначно определить состояние, существенное для безопасного управления, EnergyATS не должен его угадывать.

### REQ-PRINCIPLE-05. Аппаратные блокировки являются частью модели

Аппаратные взаимные блокировки основных контакторов `Сеть / Генератор` и генераторных контакторов `A / B` являются частью реальной схемы.

Штатное состояние, допускаемое физической схемой, не должно объявляться программной аварией.

### REQ-PRINCIPLE-06. Никакого незапланированного зацикливания

После неожиданного отказа EnergyATS не должен бесконечно повторять запуск, fallback или силовое переключение. Автоматическая цепочка fallback в одной сессии ограничена одним переходом `PRIMARY -> SECONDARY`, если отдельным требованием явно не задано иное.

### REQ-PRINCIPLE-07. Ownership внешнего запуска

Сам факт `RUNNING` генератора не даёт EnergyATS права управлять его запуском, заслонкой или остановкой. Исключение для завершения outage-related run после восстановления Grid описано отдельно ниже.

## 3. Логические уровни

### 3.1. Energy Supervisor (ES)

ES отвечает за политику: нужен ли генератор, какой генератор принадлежит текущей управляемой сессии, нужен ли fallback, когда переключать дом и когда завершать сессию.

### 3.2. Power Transfer Controller (TPC)

TPC управляет только основными контакторами `Сеть / Генератор` через:

```text
switch.grid_power
switch.use_generator_as_power_source
```

TPC не выбирает Generator A или Generator B на общей генераторной шине: этот выбор выполняется физической схемой автоматически.

### 3.3. Generator Controller (GC)

Для каждого генератора GC отвечает за REMOTE, заслонку, запуск, подтверждение RUNNING, прогрев, готовность, cooldown, остановку и локальный fault двигателя.

GC не решает, должен ли дом питаться от данного генератора.

## 4. Основные входы и их физический смысл

### 4.1. Grid

```text
binary_sensor.grid_input_ready
```

`ON` — внешняя Grid физически присутствует и пригодна. `OFF` — отсутствует или непригодна.

```text
switch.grid_power
```

`ON` — подача Grid разрешена управляющей схемой. `OFF` — Grid намеренно запрещена.

EnergyATS обязан различать физическое исчезновение Grid и намеренное отключение Grid пользователем.

### 4.2. Выбор основного источника дома

```text
switch.use_generator_as_power_source
```

`OFF` — основные контакторы выбраны в сторону Сети. `ON` — основные контакторы выбраны в сторону генераторной шины.

Основные контакторы имеют аппаратную взаимную блокировку.

### 4.3. Подтверждение управляющих цепей

```text
binary_sensor.house_powered_by_grid
binary_sensor.house_powered_by_generator
```

Датчики подключены к цепям управления соответствующих основных контакторов, а не к независимому силовому выходу после контакторов. Поэтому они подтверждают состояние управляющей цепи, но не являются независимым измерением напряжения после силовых контактов.

Одновременное устойчивое `ON` обоих датчиков недопустимо.

### 4.4. Генераторы

```text
binary_sensor.generator_a_is_running
binary_sensor.generator_b_is_running
switch.generator_a_remote_start
switch.generator_b_remote_start
sensor.generator_a_name
sensor.generator_b_name
sensor.generator_a_model
sensor.generator_b_model
select.primary_generator
```

`RUNNING` является физическим подтверждением работы/наличия выходного напряжения генератора. `REMOTE` является управляющим сигналом и сам по себе не доказывает успешный запуск.

### 4.5. UPS / МАП

Отдельного Battery contactor нет. МАП автоматически переключает UPS-линию на АКБ при отсутствии входного питания.

`binary_sensor.ups_ready` может использоваться как диагностический признак, но не создаёт отдельный управляемый `Battery path`.

## 5. Пользовательская модель питания дома

EnergyATS различает:

- `GRID` — обычная часть дома питается от Grid;
- `GENERATOR <name>` — обычная часть дома подключена к генераторной шине и владелец шины известен;
- `GENERATOR UNKNOWN` — генераторная шина выбрана, но её владелец логически не установлен;
- `UPS_ONLY` — основная часть дома не получает питание ни от Grid, ни от генераторной шины, но UPS-линия продолжает работать от МАП/АКБ;
- `NO_POWER` — EnergyATS имеет основания считать, что питание отсутствует полностью;
- `UNKNOWN` — данные противоречивы или недостаточны.

Пользовательское русское описание `UPS_ONLY`: **«В доме работает только UPS линия»**.

## 6. Генераторная шина

### REQ-BUS-01. Два генератора могут работать одновременно

```text
A RUNNING = ON
B RUNNING = ON
```

является штатным состоянием и не является аварией.

### REQ-BUS-02. Владельцем шины является один генератор

Если работает один генератор — он владелец генераторной шины. Если работают оба — владельцем остаётся тот, кто первым реально создал напряжение и втянул свой генераторный контактор.

### REQ-BUS-03. Одновременное владение невозможно

Аппаратная электрическая и механическая блокировка исключает одновременное подключение A и B к общей генераторной шине.

### REQ-BUS-04. Второй работающий генератор не отбирает шину

Если A уже владеет шиной и затем запускается B, шина остаётся за A до потери A способности удерживать контактор. Аналогично для B.

### REQ-BUS-05. Автоматическая передача шины

Если текущий владелец остановился, а второй генератор уже работает, второй аппаратно получает шину без команды EnergyATS.

### REQ-BUS-06. EnergyATS ведёт логического владельца шины

Логическое состояние владельца:

```text
A
B
NONE
UNKNOWN
```

Достоверно известный владелец должен переживать обычный restart. Конкретный способ хранения является технической реализацией.

### REQ-BUS-07. Не угадывать владельца после потери истории

Если после restart одновременно работают A и B, а достоверной сохранённой информации о владельце нет, `bus_owner = UNKNOWN`.

### REQ-BUS-08. Отдельная нагрузка второго генератора не относится к EnergyATS

EnergyATS не учитывает и не управляет отдельной линией резервного электрокотла. Возможная дополнительная нагрузка SECONDARY не меняет логику ownership генераторной шины дома.

## 7. Запуск и restart EnergyATS

### REQ-START-01. Ожидание данных

До получения обязательных физических и конфигурационных входов аппаратные команды не выдаются.

### REQ-START-02. Устойчивая сессия переживает restart

Если до restart существовала однозначная устойчивая управляемая сессия и после restart физические состояния ей соответствуют, ownership восстанавливается без повторного запуска или ненужного силового переключения.

### REQ-START-03. Незавершённую операцию нельзя продолжать вслепую

Если restart произошёл в процессе неподтверждённой аппаратной операции и безопасное следующее действие нельзя определить однозначно, активное управление блокируется до recovery.

### REQ-START-04. Старый persistent state не обязан поддерживаться

При существенном изменении модели совместимость со старой схемой persistent state не требуется. Неподдерживаемый формат отклоняется безопасно.

## 8. Grid и потеря Grid

### REQ-GRID-01. Штатная Grid

```text
grid_input_ready = ON
grid_power = ON
use_generator_as_power_source = OFF
house_powered_by_grid = ON
house_powered_by_generator = OFF
```

— штатное питание дома от Grid.

### REQ-GRID-02. Намеренное отключение Grid

```text
grid_input_ready = ON
grid_power = OFF
```

означает исправную внешнюю Grid, намеренно отключённую пользователем. Это не запускает автоматический outage-сценарий.

### REQ-GRID-03. Outage определяется физическим входом

Автоматический outage начинается только по `binary_sensor.grid_input_ready = OFF`.

### REQ-GRID-04. UPS появляется автоматически

При исчезновении входного питания МАП автоматически переводит UPS-линию на АКБ. EnergyATS не формирует команду `connect_battery`.

---

## 9. Автоматический запуск при потере Grid

### REQ-AUTO-01

При `grid_input_ready = OFF` и разрешённом АВР EnergyATS выдерживает `grid_failure_delay` (текущее значение 5 с).

### REQ-AUTO-02

Во время задержки основная часть дома остаётся без обычного источника, UPS-линия работает от МАП/АКБ (`UPS_ONLY`).

### REQ-AUTO-03

Для новой управляемой сессии используется текущий `select.primary_generator`, если слот разрешён политикой EnergyATS.

### REQ-AUTO-04

EnergyATS подаёт один уровневый REMOTE START выбранному PRIMARY. Внутреннее количество попыток пуска двигателя определяет DKG116; EnergyATS не создаёт собственный цикл многократного ON/OFF REMOTE.

### REQ-AUTO-05

До подтверждённого RUNNING и готовности PRIMARY дом не переводится на генераторную шину.

### REQ-AUTO-06

После готовности PRIMARY переход выполняется break-before-make:

1. `grid_power -> OFF`;
2. подтвердить снятие сетевой управляющей ветви;
3. `use_generator_as_power_source -> ON`;
4. подтвердить генераторную управляющую ветвь.

---

## 10. Ручной запуск через EnergyATS

### REQ-MANUAL-01

Ручная команда EnergyATS создаёт управляемую сессию текущего PRIMARY.

### REQ-MANUAL-02

Наличие исправной Grid само по себе не отменяет вручную созданную генераторную сессию.

### REQ-MANUAL-03

Дом переводится на генератор только после успешного запуска и готовности управляемого генератора.

### REQ-MANUAL-04

Повторная команда запуска при активной управляемой сессии не создаёт вторую сессию.

---

## 11. Внешний запуск генератора

### REQ-EXT-01

Генератор, который работает, но не принадлежит текущей управляемой сессии EnergyATS, считается внешне работающим.

### REQ-EXT-02

По умолчанию EnergyATS не управляет REMOTE, заслонкой или остановкой внешне работающего генератора.

### REQ-EXT-03

Наличие внешне работающего второго генератора во время управляемой сессии допустимо. EnergyATS не объявляет «нарушение взаимной блокировки генераторов», не изолирует шину только по факту второго RUNNING и не останавливает внешний генератор.

### REQ-EXT-04

Внешне работающий SECONDARY не становится managed только потому, что физически получил генераторную шину.

---

## 12. Автоматический fallback

Fallback разрешён только для управляемой сессии EnergyATS.

### REQ-FALLBACK-01. PRIMARY не запустился

Если PRIMARY не подтвердил успешный запуск/готовность и SECONDARY не работает внешне, EnergyATS выполняет один автоматический fallback на SECONDARY.

### REQ-FALLBACK-02. PRIMARY остановился до устойчивой нагрузки

Если управляемый PRIMARY неожиданно остановился до устойчивого питания дома и SECONDARY не работает, выполняется один fallback на SECONDARY.

### REQ-FALLBACK-03. PRIMARY остановился под нагрузкой

Если PRIMARY был управляемым владельцем шины и остановился под нагрузкой:

- если SECONDARY не работает — EnergyATS запускает SECONDARY как управляемый fallback;
- если SECONDARY уже работает внешне — применяется REQ-FALLBACK-05.

### REQ-FALLBACK-04. Без ping-pong

Автоматическая цепочка ограничена `PRIMARY -> SECONDARY`. Если SECONDARY также отказал, EnergyATS не возвращается автоматически к PRIMARY; дальнейшее автоматическое управление генераторами прекращается и требуется recovery/решение пользователя.

### REQ-FALLBACK-05. Уже внешний SECONDARY нельзя захватывать

Если SECONDARY уже работает внешне при отказе PRIMARY, EnergyATS не включает его REMOTE, не переводит его GC в managed и не записывает его как «запущенный EnergyATS».

Если PRIMARY был владельцем шины, после его остановки физическая схема автоматически передаст шину работающему SECONDARY. EnergyATS учитывает нового физического owner, но ownership двигателя остаётся внешним.

## 13. Outage-related run и TEST_RUN

### Определение

`outage-related run` — работа генератора, начавшаяся при физически отсутствующей Grid (`grid_input_ready = OFF`), если этот запуск не был явно помечен как `TEST_RUN`.

Запуск может быть создан EnergyATS, пользователем локально или другой автоматикой.

`TEST_RUN` является явным исключением: восстановление Grid само по себе не завершает тестовый запуск.

### REQ-OUTRUN-01. Классификация должна переживать restart

Для каждого работающего генератора EnergyATS должен сохранять достаточно информации, чтобы после restart различать как минимум:

```text
OUTAGE_RELATED
TEST_RUN
OTHER_EXTERNAL
```

Конкретный механизм хранения является технической реализацией.

### REQ-OUTRUN-02. Стабильная Grid завершает outage-related runs

Если генераторы были запущены во время отсутствия Grid и их работа не является `TEST_RUN`, после непрерывного восстановления Grid в течение `grid_restore_stable_time` потребность в них считается завершённой.

EnergyATS должен:

1. вернуть дом на Grid по обычной последовательности break-before-make;
2. подтвердить снятие дома с генераторной шины;
3. остановить **все продолжающие работать outage-related генераторы**;
4. для работающего двигателя выполнить штатный cooldown перед REMOTE OFF.

Правило применяется независимо от того, кто инициировал запуск конкретного outage-related генератора.

### REQ-OUTRUN-03. Ограниченное право остановки внешнего outage-related генератора

Остановка внешне запущенного outage-related генератора после устойчивого восстановления Grid является **явно разрешённым исключением** из общего правила REQ-EXT-02.

Это исключение не превращает внешний генератор в managed и не даёт EnergyATS права управлять им в других сценариях.

### REQ-OUTRUN-04. TEST_RUN не останавливается по возврату Grid

Генератор, явно классифицированный как `TEST_RUN`, не должен автоматически останавливаться только потому, что Grid восстановилась или стабильна.

## 14. Возврат на Grid

### REQ-RETURN-01

В outage-сессии после `grid_input_ready = ON` EnergyATS ждёт непрерывную стабильность Grid `grid_restore_stable_time` (текущее значение 60 с).

### REQ-RETURN-02

До окончания выдержки дом остаётся на текущем генераторном источнике, если он доступен.

### REQ-RETURN-03

Возврат выполняется break-before-make: снять генераторную ветвь, подтвердить `house_powered_by_generator = OFF`, выбрать сторону Сети, разрешить `grid_power = ON`, подтвердить сетевую управляющую ветвь.

### REQ-RETURN-04

После снятия дома с генераторной шины управляемые и outage-related генераторы останавливаются согласно ownership/run-context правилам. Генераторы `TEST_RUN` не останавливаются по этому основанию.

---

## 15. Ручная остановка управляемой сессии

### REQ-STOP-01

Ручная команда остановки сначала снимает дом с генераторной ветви.

### REQ-STOP-02

Управляемый генератор не останавливается под нагрузкой по штатной команде EnergyATS.

### REQ-STOP-03

После подтверждённого снятия нагрузки GC выполняет cooldown и REMOTE OFF управляемого генератора.

### REQ-STOP-04

Ручная остановка управляемой сессии сама по себе не даёт права остановить внешний генератор, если тот не является outage-related и не подпадает под REQ-OUTRUN-02.

---

## 16. Неконсистентные и аварийные состояния

Проверки подтверждений применяются после допустимого времени физического переключения, а не мгновенно в тот же тик, когда выдана команда.

### REQ-FAULT-01

`house_powered_by_grid = ON` и `house_powered_by_generator = ON` одновременно — недопустимо.

### REQ-FAULT-02

Если `use_generator_as_power_source = ON`, есть хотя бы один RUNNING generator, а `house_powered_by_generator = OFF` и подтверждение не появляется за timeout — это неисправность переключения или обратной связи.

### REQ-FAULT-03

Если `use_generator_as_power_source = OFF`, `grid_power = ON`, `grid_input_ready = ON`, а `house_powered_by_grid = OFF` и подтверждение не появляется за timeout — это неисправность переключения или обратной связи.

### REQ-FAULT-04

Если `grid_power = OFF`, но `house_powered_by_grid = ON` в устойчивом состоянии — это противоречие управляющей схемы.

### REQ-FAULT-05

Если `house_powered_by_generator = ON`, но оба `generator_*_is_running = OFF` в устойчивом состоянии — это неконсистентность.

### REQ-FAULT-06

Одновременный RUNNING A и B не является fault.

---

## 17. Повторное исчезновение Grid во время возврата

Если Grid снова пропала до начала силового возврата и дом остаётся на работающем генераторе, возврат отменяется. Начатая операция основных контакторов не разворачивается вслепую посередине: текущий безопасный шаг сначала доводится до подтверждённого состояния.

Если управляемый генератор ещё работает и готов, он может быть повторно использован без нового холодного запуска.

## 18. Emergency Stop и Recovery

Активный общий Emergency Stop имеет приоритет над обычными сценариями. При Emergency Stop новые команды запуска запрещены.

`RECOVERY_REQUIRED` используется, когда безопасное продолжение активного управления невозможно определить однозначно: потеряна незавершённая транзакция, данные противоречат друг другу, подтверждение не пришло за timeout, после restart невозможно восстановить ownership незавершённой операции, либо SECONDARY после fallback также отказал.

Recovery не даёт EnergyATS права останавливать внешний генератор, кроме явно разрешённого завершения outage-related run после устойчивого восстановления Grid.

## 19. Пользовательский статус и лог

Пользовательский UI и журнал используют реальные имена генераторов, а не A/B.

Физическая доступность внешней Grid отображается отдельно (`Grid=ON/OFF`).

Режим питания отображается как минимум как:

```text
Grid
Generator <name>
Generator Unknown
UPS ONLY
NO POWER
Unknown
```

При двух RUNNING это отображается как нормальный факт; отдельно показывается известный `bus_owner`.

---

## 20. Что не должно существовать в доменной модели как физический механизм

EnergyATS не должен моделировать как реально существующие исполнительные устройства:

- отдельный Battery contactor;
- отдельную команду `connect_battery`;
- программный selector `Generator A / Generator B` для общей генераторной шины;
- запрет одновременного RUNNING двух генераторов.

Допустимы вычисляемые состояния `UPS_ONLY`, `bus_owner`, `run_context` и т.п., если они описывают реальную физику.

## 21. Минимальные сценарные тесты

1. штатная Grid;
2. физическая потеря Grid;
3. `grid_power = OFF` при физически исправной Grid;
4. `UPS_ONLY`;
5. автоматический запуск PRIMARY;
6. ручной запуск PRIMARY;
7. возврат на Grid;
8. оба генератора RUNNING одновременно;
9. внешний SECONDARY запускается во время managed-сессии;
10. PRIMARY останавливается, внешний SECONDARY аппаратно получает шину;
11. PRIMARY не запускается, SECONDARY выключен -> managed fallback;
12. PRIMARY останавливается, SECONDARY выключен -> managed fallback;
13. SECONDARY после fallback также не запускается -> recovery без ping-pong;
14. restart при двух RUNNING и сохранённом owner;
15. restart при двух RUNNING без owner -> UNKNOWN без угадывания;
16. outage-related внешний генератор останавливается после стабильной Grid;
17. два outage-related генератора оба останавливаются после стабильной Grid;
18. TEST_RUN не останавливается по возврату Grid;
19. противоречивые `house_powered_by_*`;
20. timeout подтверждения основных контакторов;
21. повторная потеря Grid при возврате;
22. Emergency Stop;
23. recovery после незавершённой транзакции.

## 22. Порядок изменения системы

Если меняется физическая схема:

```text
PHYSICAL_POWER_TOPOLOGY_RU.md
        ->
REQUIREMENTS_RU.md
        ->
код EnergyATS
        ->
автоматические тесты
        ->
физические испытания
```

Если меняется только политика автоматики, физическая схема не переписывается.

# Energy ATS 0.3.0 — архитектура

## Зачем понадобилось разделение

Версия 0.2.x решала сразу три разные задачи: выбирала источник энергии,
переключала силовые контакторы и знала особенности запуска Elemax и Вепря.
Такой автомат работал, но каждое новое правило увеличивало один общий FSM.

В 0.3.0 приложение остаётся **одним процессом и одним Home Assistant App**, но
внутри разделено по предметной ответственности:

| Модуль | Единственный вопрос, на который он отвечает |
|---|---|
| `energy_supervisor.py` | Какой источник сейчас нужен дому и зачем? |
| `power_transfer.py` | Как безопасно привести силовые контакторы к выбранному источнику? |
| `generator_controller.py` | Как запустить, подготовить и остановить конкретный двигатель? |
| `ha_adapter.py` | Какие HA-сущности соответствуют входам и физическим командам? |
| `main.py` | Как связать эти контроллеры, журнал и WebSocket в одном процессе? |

Контроллеры не общаются друг с другом через Home Assistant entities. Они
обмениваются обычными Python-структурами в памяти, поэтому система не стала
распределённой и не приобрела дополнительные сетевые точки отказа.

## Контракт между уровнями

Supervisor выдаёт две уровневые цели:

```python
desired_source = GRID | BATTERY | GENERATOR_A | GENERATOR_B

desired_generators = {
    A: True | False,
    B: True | False,
}
```

Это именно желаемые состояния, а не импульсные команды. Supervisor не знает,
как двигается заслонка и какой контактор надо выключить первым.

`GeneratorController` возвращает Supervisor только состояние своего объекта:

```python
running
remote_on
ready_for_load
externally_started
fault
phase
```

`PowerTransferController` возвращает:

```python
actual_source
target_source
transition_in_progress
recovery_required
fault
```

Главное ограничение интерфейса: Power Transfer никогда не подключает
генераторную шину, пока соответствующий Generator Controller не сообщил
`ready_for_load=True`.

На самой границе service calls `ha_adapter.py` повторно проверяет минимальные
физические предусловия. Он отдельно отклонит попытку включить второй REMOTE,
сделать make-before-break или снять REMOTE с работающего генератора, пока дом
подтверждённо находится на его шине. Это последний предохранитель, а не
энергетическая политика.

## Generator Controller

Для каждого двигателя используется один и тот же автомат:

```text
IDLE
→ PREPARING
→ WAITING_FOR_RUNNING
→ CHOKE_HOLD
→ WARMING_UP
→ READY_FOR_LOAD
→ WAITING_FOR_LOAD_RELEASE
→ COOLING_DOWN
→ WAITING_FOR_STOP
→ IDLE
```

Он выполняет только жизненный цикл двигателя:

- выбирает положение заслонки;
- подаёт REMOTE DKG116;
- ждёт реальный `generator_*_is_running`;
- открывает заслонку после запуска;
- выдерживает прогрев;
- сообщает готовность к нагрузке;
- перед остановкой ждёт физического снятия нагрузки;
- выполняет cooldown;
- снимает REMOTE и подтверждает остановку.

DKG116 по-прежнему сам выполняет прокрутку и собственные попытки запуска.
Generator Controller не дублирует стартерную автоматику DKG116.

### Профили конкретных двигателей

Имена, модели и стратегия заслонки больше не являются настройками ATS. Они
собраны в одном явно отмеченном блоке `default_generator_profiles()` файла
`generator_controller.py`.

Текущие профили:

- A / Elemax — заслонка используется при каждом управляемом запуске;
- B / Вепрь — заслонка используется при
  `ambient_temperature_external < 10 °C`;
- неизвестная температура означает консервативный холодный запуск;
- времена прогрева: 30 / 60 / 180 / 300 секунд;
- cooldown: 300 секунд.

`ambient_temperature_external` сейчас читается из
`sensor.garage_temperature`. Это внешний ориентир для Python-контроллера, а
не датчик ESP32. В `generator-controller.yaml` он не импортируется. Когда
появится датчик температуры двигателя, источник можно заменить внутри этого
слоя, не меняя Supervisor и Power Transfer.

## Power Transfer Controller

Этот автомат не выбирает A или B и не решает, нужен ли генератор. Его
обязанности ограничены силовой безопасностью:

- физическая обратная связь является источником истины;
- всегда используется break-before-make;
- каждый шаг имеет timeout подтверждения;
- возврат при отсутствующей Grid ведёт на normal path МАП/аккумуляторов;
- двигатель никогда не останавливается этим модулем;
- отказавший источник изолируется, но второй генератор здесь не запускается.

Переход на генератор:

```text
READY_FOR_LOAD
→ Grid power OFF
→ подтверждение House Grid OFF
→ selector Generator
→ подтверждение House Generator ON
```

Возврат:

```text
selector Normal
→ подтверждение House Generator OFF
→ Grid power ON
→ подтверждение Grid либо режима МАП от аккумуляторов
```

## Energy Supervisor

Supervisor владеет длительной генераторной сессией и причиной её появления:

- `MANUAL_BACKUP` — ручная кнопка;
- `GRID_OUTAGE` — автоматическая политика при разрешённом АВР;
- `BATTERY_CHARGE` и `TEST_RUN` зарезервированы для будущих сценариев.

В 0.3.0 реализована консервативная политика:

- одновременно запрашивается не более одного генератора;
- новый запуск запрещён, если у любого агрегата уже активны RUNNING или REMOTE;
- при отказе выбранного агрегата генераторная шина изолируется;
- автоматический запуск второго агрегата **не выполняется**;
- выбор fallback в будущем будет решением Supervisor, а не аварийной реакцией
  Power Transfer Controller.

### Ручная сессия

Кнопка `Включить резервное питание` создаёт управляемую ручную сессию и вводит
выбранный генератор. Повторное нажатие не создаёт второй запуск.

Кнопка `Остановить генератор` означает:

1. вернуть дом на normal path;
2. подтвердить снятие нагрузки;
3. выполнить cooldown в Generator Controller;
4. остановить управляемый двигатель.

Если Grid отсутствует, шаг 1 штатно возвращает UPS-линию на питание от
аккумуляторов МАП. Команда не блокируется и предупреждение «Grid Input Ready =
OFF» не создаётся. Чтобы АВР не отменил ручное решение, автоматический
запуск подавляется до возврата Grid или новой ручной команды запуска.

Если ручная сессия была начата во время отсутствия Grid, а затем Grid стабильно
вернулась, дом автоматически возвращается на Grid. Сам генератор остаётся
работать, поскольку ручное намерение RUN не отменялось. После заданной выдержки
Supervisor напоминает, что генератор работает без нагрузки, но в 0.3.0 не
останавливает его сам.

Если ручная сессия была начата при уже доступной Grid, само наличие Grid не
отменяет введённое пользователем резервное питание.

Если после возврата дома на normal path человек локально остановил уже
разгруженный управляемый генератор, Supervisor только подтверждает завершение
ручной сессии. Повторных команд остановки и ложного recovery не создаётся.

### Внешний или локальный запуск

Работающий генератор без принадлежащей Supervisor сессии считается внешним.
В этом режиме система:

- распознаёт запуск;
- показывает статус и отправляет уведомление;
- не двигает заслонку;
- не включает и не снимает REMOTE;
- не переключает дом;
- не останавливает двигатель;
- не «захватывает» его после появления команды Supervisor.

## Транзакции и потеря Home Assistant

Транзакция здесь — не database rollback. Это сохраняемая запись о физической
цепочке действий: цель, текущий шаг, последнее подтверждение и список команд,
которые были записаны, но ещё не подтверждены завершением service call.

Перед каждой аппаратной командой `main.py` атомарно записывает
`/data/energy-supervisor-state.json`. После успешного выполнения pending-список
очищается второй записью.

Правило восстановления:

- потеря HA в устойчивом состоянии не меняет положение оборудования;
- работающий управляемый генератор в устойчивой сессии после restart может
  снова быть признан своим по журналу и физической обратной связи;
- потеря HA или restart во время незавершённой физической транзакции переводит
  систему в `RECOVERY_REQUIRED`;
- сохранённая устойчивая сессия восстанавливает ownership только при совпадении
  ожидаемого и фактического источника; расхождение не исправляется вслепую;
- кратковременно неизвестное состояние обязательного датчика замораживает
  автоматы без команд и не стирает последнюю подтверждённую фазу;
- прерванная цепочка не продолжается автоматически и не откатывается вслепую;
- после осмотра оператор приводит систему к однозначному normal path и нажимает
  `Сбросить ошибку ATS`.

В 0.3.0 автоматическая коррекция положения заслонки после потери HA намеренно
не добавлена. Это отдельное safety-решение, которое следует принимать после
реальной эксплуатации и анализа конкретного сценария отказа.

## Роль ESPHome YAML

`generator-controller.yaml` версии 0.3.0 остаётся тонким аппаратным слоем:

- GPIO RUNNING;
- физические REMOTE и Emergency Stop;
- взаимоисключающие ограниченные импульсы приводов заслонок;
- SDM120, SmartShunt и модель топлива;
- отсутствие reboot ESP32 при потере API HA.

В YAML нет сценария запуска, температуры гаража, прогрева, cooldown или выбора
источника дома. Добавлены четыре однозначные команды:

```text
button.generator_a_choke_to_cold
button.generator_a_choke_to_run
button.generator_b_choke_to_cold
button.generator_b_choke_to_run
```

Старые кнопки `choke_open/choke_close` временно сохранены для безопасного
обновления с 0.2.5, но код 0.3.0 их не использует.

Версии Home Assistant App и прошивки Generator Controller независимы. Для
первого согласованного релиза обе имеют номер `0.3.0`; версия ESPHome объявлена
в `esphome.project.version`.

## Что пока сознательно не реализовано

- автоматический fallback A → B;
- автоматическая остановка вручную запущенного двигателя на холостом ходу;
- запуск по SoC и завершение зарядной сессии;
- управление током зарядки МАП;
- энергетическая оценка по P/S/I/PF;
- автоматическое продолжение прерванных транзакций.

Для этих функций теперь есть подходящий верхний уровень — Energy Supervisor,
но добавлять их можно по отдельности, не смешивая с безопасной коммутацией и
процедурой запуска двигателя.
